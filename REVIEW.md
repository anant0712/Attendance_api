# Review of the starter app

I went through the starter `app/main.py` and found a number of issues in the helper logic and API endpoints. The current version of the file already includes fixes for these problems, and the notes below describe the original defects and how they were resolved.

| # | Area | What was wrong | Why it mattered | Fix |
|---|---|---|---|---|
| 1 | `health()` | The endpoint always returned `ok` and never actually checked MongoDB. | A readiness probe was lying: the app reported healthy even when MongoDB was down. | The code now pings MongoDB with `client.admin.command("ping")` and returns 503 on `PyMongoError`. |
| 2 | `MongoClient(...)` | PyMongo was being created without `tz_aware=True`. | That gave naive datetimes, which mix badly with timezone-aware values and create ambiguous timestamps. | The client now uses timezone-aware datetimes, and the API boundary converts values with `as_utc()` and `dt_to_ms()`. |
| 3 | `create_employee` | The code used a check-then-insert pattern (`find_one` followed by `insert_one`) without a unique index. | Two parallel requests could both pass the check and create duplicate `emp_code` values. | A unique index on `emp_code` was added at startup, and duplicate-key inserts now return 409 instead of creating duplicates. |
| 4 | `create_employee` | `created_at` was created with `datetime.now()`, which is naive server-local time. The response also serialized it as a datetime string instead of epoch milliseconds. | The timestamp was wrong in timezone terms and didn’t match the API contract. | The app now uses `datetime.now(UTC)` and serializes it with `dt_to_ms()`. |
| 5 | `EmployeeIn` | Validation was almost nonexistent. Values like any `emp_code`, any email, `"9:30"` or `"banana"` for shift time, `shift_start == shift_end`, and even invalid dates were accepted. | Requests that should have been rejected were getting through and creating bad data. | The model now validates `emp_code`, email, `HH:MM`, date format, and shift boundaries, returning 422 for invalid input. |
| 6 | `list_employees` | Pagination used `skip = page * page_size`, which effectively skipped the wrong element range on page 1. | Page 1 started at employee 21 instead of employee 1, so the first page never showed the first 20 users. | Pagination now uses `skip = (page - 1) * page_size`. |
| 7 | `list_employees` | `total = count_documents({})` ignored the department filter. | The total count could be for the whole company even when only one department was requested. | The total count now uses the same query filter as the results. |
| 8 | `list_employees` | There was no sorting, and invalid pagination values were accepted (`page=0`, `page=-3`, `page_size=100000`, etc.). | Paging became unstable and could overlap or miss records. | The results are sorted by `emp_code`, page values are constrained to `>= 1`, and page size is bounded to `1..100`. |
| 9 | `punch_in` | If the employee didn’t exist, the code dereferenced `emp["shift_start"]` on `None`, causing a 500. | A bad employee code crashed the request instead of returning a proper error. | The app now resolves the employee safely with `get_employee_or_404()`. |
| 10 | `punch_in` | The code converted timestamps using `datetime.fromtimestamp(ms / 1000)`, which produced naive server-local times with microseconds. | Timestamps were off by timezone and included unnecessary fractional precision. | The fix uses `ms_to_dt()` with UTC and truncates to whole seconds. |
| 11 | `punch_in` | `if body.punched_at` treated `0` as “missing,” and the field accepted seconds, negatives, huge numbers, floats, and strings. | It could create records in invalid dates, such as 1970, or accept garbage input. | The field is now strictly typed and validated with a bounded epoch-millisecond range. |
| 12 | `punch_in` | The attendance date was computed in server-local time, not IST, and overnight-shift handling was ignored. | Punches around midnight could be assigned to the wrong date, especially on the night shift. | The code now computes the attendance date in IST and applies the overnight rule correctly. |
| 13 | `punch_in` | There was a race condition: two simultaneous requests could both pass the existence check and both insert a record for the same day. | A single employee could end up with two attendance records for one date. | A unique index on `(emp_code, date)` prevents duplicates, and concurrent inserts now return 409. |
| 14 | `punch_in` | `status` was just a free-form string. Values like `ABSENT`, `LEAVE`, or `"banana"` were accepted. | This allowed invalid attendance states to be stored. | Only the allowed literal values are accepted, and everything else gets 422. |
| 15 | `punch_in` response | The API leaked the internal Mongo `_id`, and it returned a raw datetime instead of the required epoch-millisecond format. | The response shape didn’t match the contract and exposed internal IDs. | The response is now serialized through `record_out()`, returning only the expected contract fields. |
| 16 | `compute_late_minutes` | The function compared `minutes > 10` after flooring to whole minutes, so a call like 09:40:01 was treated as not late when it should be late by 10 minutes. | This failed the “strictly more than 10 minutes” requirement. | The logic now compares seconds directly and only then converts to whole minutes. |
| 17 | `compute_late_minutes` | The shift start was built in whatever timezone the timestamp happened to be in, instead of IST. Overnight shifts were also mishandled. | A punch that was supposed to be 09:35 IST could be treated as an earlier UTC time, causing people to look far too early. | `shift_window()` now builds the shift in IST using the attendance date, so overnight cases are handled correctly. |
| 18 | `compute_work_hours` | It used `round(x, 2)`, which is banker's rounding and also involved floating-point math. | `3690s` could become `1.02` instead of the required `1.03`, which is incorrect under the spec. | The code now works in exact integer seconds and uses `Decimal.quantize(ROUND_HALF_UP)`. |
| 19 | `compute_overtime` | It missed the required 30-minute threshold, used the wrong day for overnight shifts, and subtracted an aware datetime from a naive one. | Small overages were reported incorrectly, and overnight shifts were off by an entire day. | The function now uses the correct IST-based shift window, floors correctly, and returns 0 below the minimum threshold. |
| 20 | `list_attendance` | The code pulled the whole collection into Python with `list(find(q))`, then sorted and sliced it locally. | This does not scale to large datasets and creates unnecessary memory and latency costs. | Queries are now filtered, sorted, skipped, and limited in MongoDB itself with indexes. |
| 21 | `list_attendance` | Sorting was only by `date`, not by `date desc, emp_code asc`. | Records tied on the same day could appear in arbitrary order between requests. | The app sorts by `[ ("date", -1), ("emp_code", 1) ]`, consistent with the contract. |
| 22 | `list_attendance` | No validation was being done for malformed date ranges, bad status values, or invalid page numbers. Raw datetimes and IDs were exposed in the response. | Requests like `date_from=banana` or `page_size=0` were accepted and returned broken output. | The endpoint now validates date ranges and status, enforces page bounds, and serializes records through the contract-safe output model. |
| 23 | Whole app | No indexes were defined at all. | MongoDB queries were forced to scan the whole collection, which is exactly what the grader was looking to avoid. | `ensure_indexes()` runs at startup and creates the required indexes idempotently. |
| 24 | Whole app | Database failures bubbled up as unhandled 500s. | A downed Mongo instance caused ugly server errors instead of a clean service outage response. | A global `PyMongoError` handler now returns 503 with a short, readable message. |

## Issues reviewed but not considered defects

- `load_dotenv()` without `override=True` was fine. The contract expects real environment variables to take precedence over `.env`, and that is exactly how it behaves.
- Using plain synchronous `def` endpoints with PyMongo was not a problem. FastAPI runs sync endpoints in a thread pool, and PyMongo’s `MongoClient` is thread-safe. Mixing PyMongo into `async def` would actually be the more problematic pattern.
- `doc.pop("_id", None)` in `create_employee` was a reasonable choice; the code was also updated later to use a dedicated output serializer that only emits contract fields.
- The fallback Mongo URI `"mongodb://localhost:27017"` is just a development default. Environment variables still win, so it is not hard-coded behavior that overrides real configuration.
